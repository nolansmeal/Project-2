# Design Log — Project 2

## Growth factor and amortized cost
For the Conversation class, I used a dynamically allocated array of Message objects. The class uses data_ to store the array, size_ to track the number of messages, and capacity_ to track how many messages can fit in the current allocation. An empty conversation starts with size and capacity equal to zero and data_ set to nullptr. When append() is called and the array is full, the capacity increases. The first allocation changes the capacity from 0 to 1, and after that the capacity doubles, resulting in capacities of 1, 2, 4, 8, 16, and so on. A larger array is allocated, the existing messages are copied into it, and the old array is deleted. Although resizing requires copying messages, it does not happen on every append. With doubling, the total number of elements copied across n appends follows 1 + 2 + 4 + 8 + ... and stays below 2n. Therefore, the total copying work is O(n), giving append() an amortized cost of O(1).


## Rule of Five evidence
The Conversation class manages dynamically allocated memory, so I implemented the Rule of Five: a destructor, copy constructor, copy assignment operator, move constructor, and move assignment operator. The destructor uses delete[] to release the Message array. The copy constructor performs a deep copy by allocating a separate array and copying each message. This prevents the original and copied conversations from sharing the same memory. My test verifies this by checking that their begin() pointers have different addresses. The copy assignment operator also creates a separate copy. It checks for self-assignment, allocates the required memory, copies the messages, deletes the old array, and updates the object's data. The move constructor and move assignment operator transfer the data_ pointer, size_, and capacity_ instead of copying every message. The original object's data_ is then set to nullptr and its size and capacity are set to zero. My move test verifies that the new conversation receives the original array address and that the original conversation becomes empty.


## Sentinel scanner: bounded pending_ proof
The SentinelScanner searches streamed text for <|end_conversation|>. Because the text arrives in chunks, the sentinel may begin in one chunk and finish in another. The scanner uses pending_ to temporarily hold characters that could be part of the sentinel. Each time feed() receives a chunk, it combines pending_ with the new text and searches for the sentinel. If the sentinel is found, only the text before it is returned as safe text. If the sentinel is not found, the scanner keeps at most sentinel_.size() - 1 characters from the end. If the sentinel has length L, pending_ therefore contains at most L - 1 characters after each call. Any earlier characters cannot combine with future input to create a complete sentinel, so they are safe to return. This keeps pending_ bounded instead of allowing it to grow with the total stream. I tested normal text, false sentinel patterns, every possible split position of the sentinel, and a large adversarial input containing repeated partial sentinel patterns. The adversarial input is fed one character at a time to test the scanner across very small chunk boundaries.


## What I would change differently
If I improved this project, I would focus on making debugging and testing easier. During development, temporary debugging information showing whether the harness stopped because of the sentinel, turn limit, or EOF was helpful for finding problems. I would also design more of my tests before implementing the classes. Testing cases such as EOF, sentinel detection, and adversarial input earlier would have made the expected behavior and edge cases clearer. Overall, this project helped me better understand dynamic memory, pointers, copy and move operations, growable arrays, and processing streamed data.
